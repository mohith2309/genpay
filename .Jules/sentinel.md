## 2026-07-13 - Node.js Stream Unhandled Rejection on req.destroy()

**Vulnerability:** Denial of Service (DoS) and Information Disclosure in custom Node.js server.
**Learning:** When manually handling HTTP request streams using `req.on('data')` to implement payload size limits, calling `req.destroy()` correctly aborts the connection but fails to automatically reject or resolve the wrapping Promise. Without an explicit `reject()`, the Promise hangs indefinitely, causing a server-side memory leak. Additionally, global error handlers commonly catch deep operational errors but expose them via `e.message` to the client, leading to Information Disclosure. Furthermore, when abruptly destroying an incoming stream in response to a size violation, if the application has already entered a global error state and attempted to resend a response, it triggers an `ERR_HTTP_HEADERS_SENT` crash.
**Prevention:** Always explicitly call `reject(new Error(...))` alongside `req.destroy()` when terminating streams early inside Promises. Always include a short-circuit check `if (res.headersSent) return;` in common response/send helper functions to prevent duplicate response crashes. Never expose raw error messages (like `e.message`) in 500 error catch blocks; mask them with generic strings.
